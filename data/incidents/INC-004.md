## Summary

`reporting-api` saturated CPU on all 4 instances between 11:22 and 13:05 UTC
on 2026-05-19, degrading report generation without a full outage. The root
cause was a newly released report query containing an unindexed join against
`analytics-db`, which triggered full table scans on a 1.4 billion row table.
Service was restored at 13:05 UTC by adding a composite index. Total
degradation lasted 1 hour 43 minutes.

## Trigger and recent changes

At 11:15 UTC, `reporting-api v4.4.0` was deployed, adding a new customer
revenue report. The new report query joined `order_events` to
`customer_organizations` without an index on
`customer_organizations.external_ref`.

Seven minutes later, at 11:22 UTC, CPU on all 4 `reporting-api` instances
rose from an average of 25% to 98%. A scheduled report job began running at
11:20 UTC and executed the new query across all customers in parallel.

## Symptoms

- CPU at 98% on all 4 `reporting-api` instances, sustained.
- Report generation times rose from 12 s median to over 20 minutes.
- Database CPU on `analytics-db` rose to 91% as a consequence of the scans.
- `pg_stat_activity` showed continuous sequential scans on
  `customer_organizations`.
- No 5xx responses. The service degraded rather than failed, which is why this
  was SEV-3 rather than higher.
- `payments-api` unaffected, on a separate database and cluster.

## Root cause

An unindexed join in a newly released report query. The query in
`reporting-api v4.4.0` joined `order_events` to `customer_organizations` on
an unindexed column, causing a sequential scan of a 1.4 billion row table for
every row of `order_events`. The query was functionally correct and returned
correct results, which is why it passed functional testing, but its execution
plan was not reviewed before release.

The root cause is a missing index combined with the absence of a query plan
gate in CI.

## Impact and blast radius

Infrastructure:
- 4 of 4 `reporting-api` instances CPU saturated.
- `analytics-db` CPU at 91%, a secondary victim.
- No customer-facing transaction systems affected.

Services:
- `reporting-api` severely degraded.
- `payments-api`, `orders-api`, `auth-gateway` unaffected.
- Internal finance reporting team blocked for the duration.

Users:
- 340 internal users affected, all reporting-api customers.
- 0 external end users affected directly.
- 28 scheduled reports failed or timed out.

Requests:
- 1,900 report requests failed or timed out.

Data:
- No data loss. All reads.
- No incorrect results were produced. The query was slow, not wrong, which is
  the one mercy in this incident.
- 0 records corrupted.

## Timeline

- 11:15 - `reporting-api v4.4.0` deployed. Functional tests pass.
- 11:20 - Scheduled nightly revenue report job starts.
- 11:22 - CPU on all 4 instances rises to 98%. Alert fires.
- 11:29 - Engineers identify the new revenue report query as the only new
  workload in the window.
- 11:34 - Attempt to disable the revenue report feature flag. See failed actions.
- 11:41 - Decision to add the missing index.
- 11:48 - Index build initiated with `CONCURRENTLY` on `analytics-db`.
- 12:30 - Index build complete. Query plan rechecked and confirmed to use the
  index.
- 12:35 - Report job re-run manually. Normal execution time restored.
- 13:05 - CPU returned to 24% average. Incident closed.
- 16:00 - Finance reporting team confirms all 28 reports regenerated correctly.

## Attempted actions

1. Disabling the `revenue_report_v2` feature flag, at 11:34 UTC.
2. Building a composite index on `customer_organizations`, at 11:48 UTC.
3. Re-running the revenue report job manually, at 12:35 UTC.

## Failed actions

- Disabling the `revenue_report_v2` feature flag was attempted at 11:34 UTC.
  It did not resolve the incident. The flag gates the endpoint but not the
  scheduled job, and the running job had already read the flag value at start
  time. The job continued to execute the expensive query after the flag was
  disabled, and the disable was not noticed for 45 minutes. The correct
  action under time pressure would have been to kill the running job
  explicitly, not to change a flag it had already read.

- Restarting `reporting-api` instances was considered at 11:31 UTC and rejected
  without being executed. It was correctly identified beforehand as pointless,
  because the expensive query would be reissued by the scheduler on the next
  run and the instances would re-saturate within minutes. Restarting a service
  does not change a query's execution plan.

- Killing the scheduled report job was attempted at 11:40 UTC and only
  partially succeeded. Two of four workers were terminated, but the job
  restarted itself under the scheduler's retry policy and resumed scanning.
  The scheduler's retry policy was not disabled, so the job returned. This
  delayed the index build by 8 minutes, which was spent attempting the action
  before observing that it did not hold.

## Successful actions

- Building the composite index on
  `customer_organizations(external_ref, tenant_id)` at 11:48 UTC, using
  `CREATE INDEX CONCURRENTLY` to avoid locking, was the action that resolved
  the incident. Query execution time dropped from over 20 minutes to 340 ms,
  confirmed by manual re-run at 12:35 UTC.

- Verifying the new execution plan with `EXPLAIN ANALYZE` before declaring
  resolution at 12:30 UTC confirmed the index was actually being used, rather
  than assuming the index had fixed the problem.

## Relevant runbook

`reporting-query-performance-triage` (runbook id
`reporting-query-performance-triage`) was consulted at 11:36 UTC. Its step
requiring `EXPLAIN ANALYZE` before acting is what identified the sequential
scan, and its guidance to prefer a concurrent index build over service
interruption is what kept `analytics-db` available to other services.

## Lessons learned

- A query can be correct and still be an outage. Functional correctness testing
  passed entirely; only a plan review would have caught this.
- Disabling a feature flag does not stop work already in flight. Kill the job,
  not the flag that gates the next call.
- A scheduler retry policy will resurrect a job that is still expensive. The
  retry policy has to be part of the mitigation.
- Sequential scans on large tables are a code review concern, not a query
  review concern. This should never have reached production.
- Degradation without 5xx responses is hard to alert on. The CPU alert caught
  this in 2 minutes, which was fortunate.

## Related incidents

No directly related incidents were identified at the time of writing. This is
the first recorded query performance incident in `reporting-api`, though
`analytics-db` has had two earlier near-misses that did not cause user impact.

## Prevention and follow-up

- P0: Add a CI query plan gate that runs `EXPLAIN ANALYZE` on every new query
  in a migration or report definition and fails the build on a sequential scan
  of a table above 10 million rows.
- P1: Add alerting on `pg_stat_activity` sequential scan counts.
- P1: Require an index review as part of code review for any query touching
  `order_events` or `analytics-db`.
- P2: Add a statement timeout of 30 seconds at the connection pool level for
  `reporting-api`, so a pathological query fails fast instead of consuming a
  core for 20 minutes.
- P2: Make feature flag changes take effect for in-flight scheduled jobs, or
  document clearly that they do not.
