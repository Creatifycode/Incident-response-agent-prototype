## Summary

`notification-worker` processed zero messages from 07:44 to 09:56 UTC on
2026-06-30. The worker was healthy by every infrastructure signal: no crashes,
no elevated CPU, no error rate. The root cause was a deployment that removed
a required environment variable, `NOTIFICATION_PROVIDER_API_KEY`, causing the
provider client to initialise as a no-op that silently discarded every
message. The failure mode was silence, not errors. Service was restored at
09:56 UTC by restoring the environment variable. Total duration was 2 hours
12 minutes.

This incident is notable because no monitoring signal indicated a problem. The
worker was healthy and doing nothing.

## Trigger and recent changes

At 07:36 UTC, `notification-worker v3.1.0` was deployed. The release refactored
configuration loading to read from a single mounted config file and explicitly
removed the legacy environment variable fallback path. The variable
`NOTIFICATION_PROVIDER_API_KEY` was not migrated into the new config file,
because the removal commit message described it as deprecated and the variable
was not in the migration checklist.

Eight minutes later at 07:44 UTC, the worker began dropping messages. The
worker entered its steady state, found no API key, and set its dispatch client
to a null implementation that returns success for every send.

## Symptoms

- Zero notifications delivered. 100 percent message loss.
- No exceptions, no error logs, no crash loop, no elevated CPU.
- `notification-worker` reported healthy in every dashboard.
- Queue depth on the notification broker rose steadily from 0 to 41,000
  messages over 2 hours, the only available signal.
- `payments-api` unaffected. The worker is asynchronous and downstream of
  payment authorization.

## Root cause

A broken environment variable introduced by deployment
`notification-worker v3.1.0`. The required variable
`NOTIFICATION_PROVIDER_API_KEY` was removed as a side effect of a config
loading refactor and was not set in the new configuration source. The provider
client initialised without a key and fell back to a null dispatch
implementation that reports success while discarding every message.

The deeper root cause is a fail-open design. A missing credential caused the
worker to discard work silently rather than refuse to start, and the absence
of a delivery-rate alert meant the failure was invisible to every system that
was watching.

## Impact and blast radius

Infrastructure:
- 4 of 4 `notification-worker` pods affected, all healthy, all discarding.
- No infrastructure signal degraded. This is the defining characteristic.

Services:
- `notification-worker` silently non-functional.
- `payments-api`, `orders-api`, `auth-gateway` unaffected.
- All downstream notification consumers affected: email, SMS, push.

Users:
- 19,400 users received no transactional notification of any kind.
- 100 percent notification loss for 2 hours 12 minutes.
- No user-visible error, the absence of notification is not self-reporting.

Requests:
- 41,000 messages queued and dropped, later replayed.

Data:
- No permanent data loss. All 41,000 messages were retained in the broker.
- All messages replayed successfully on 2026-07-01 between 02:00 and 05:30 UTC.
- Late-arriving order confirmation emails were sent up to 19 hours late, and
  312 customers contacted support about apparently missing receipts during the
  replay window.

## Timeline

- 07:36 - `notification-worker v3.1.0` deployed successfully. All health
  checks pass.
- 07:44 - Message delivery rate drops to zero. No alert fires.
- 08:30 - Support volume begins rising, referencing missing order
  confirmations. Not connected to the incident for 46 minutes.
- 09:05 - First engineer paged, by support escalation rather than by
  monitoring.
- 09:12 - Engineers check `notification-worker` status. Everything is healthy.
  This is the key diagnostic moment of the incident.
- 09:20 - Engineers inspect the deployment. Config refactor identified.
- 09:28 - Comparison against `v3.0.4` reveals `NOTIFICATION_PROVIDER_API_KEY`
  no longer present in the runtime environment.
- 09:34 - Attempt to set the variable via the environment endpoint. See failed
  actions.
- 09:41 - Realization that the variable must be present at process start, not
  injected at runtime.
- 09:50 - Full redeploy of `notification-worker v3.1.0` with the variable
  restored in the new config source.
- 09:56 - Delivery rate returns to 100 percent. Incident closed.
- 2026-07-01 02:00 - Replay of the 41,000 queued messages begins.
- 2026-07-01 05:30 - Replay complete.

## Attempted actions

1. Health and status inspection of `notification-worker`, at 09:12 UTC.
2. Setting `NOTIFICATION_PROVIDER_API_KEY` via the runtime environment
   endpoint, at 09:34 UTC.
3. Redeploy of `notification-worker v3.1.0` with the variable restored, at
   09:50 UTC.

## Failed actions

- Setting `NOTIFICATION_PROVIDER_API_KEY` through the runtime environment
  endpoint was attempted at 09:34 UTC. It did not resolve the incident. The
  variable was accepted by the endpoint and appeared in the pod spec, but the
  running process had already initialised its dispatch client at startup and
  did not re-read configuration. The variable was correctly present and
  correctly ignored, which cost seven minutes. A change of this kind requires
  a process restart to take effect.

- Checking `notification-worker` service health and dashboards was performed
  between 09:12 and 09:20 UTC and did not resolve the incident, because every
  health signal was green. Health checks verify that the process is running,
  not that it is doing its job. This wasted eight minutes and is a direct
  consequence of the fail-open design: the system could not report its own
  brokenness.

- Restarting `notification-worker` pods without first restoring the missing
  variable was considered at 09:22 UTC and correctly rejected. A restart
  would have re-initialised the same broken client and produced an identical
  outcome, adding another failure mode with no diagnostic value.

## Successful actions

- Diffing the runtime environment of `v3.1.0` against the known-good `v3.0.4`
  at 09:28 UTC identified the missing variable. This is the action that
  resolved the incident, and it was found by comparing against the last known
  good release rather than by reading the current configuration and reasoning
  about whether it looked correct.

- Redeploying `notification-worker v3.1.0` with
  `NOTIFICATION_PROVIDER_API_KEY` present in the new configuration source at
  09:50 UTC restored delivery to 100 percent by 09:56 UTC.

## Relevant runbook

`silent-failure-triage` (runbook id `silent-failure-triage`) was consulted at
09:22 UTC. Its first step, when every health signal is green but behaviour is
wrong, diff the runtime configuration against the last known good deployment,
is the 09:28 UTC action that found the missing variable. The runbook's
framing of a silent failure as a distinct incident class was written after
this incident and did not exist at the time.

## Lessons learned

- A fail-open design is the real defect. A worker with no credentials should
  refuse to start or crash loudly, not accept every message and throw it away
  while reporting success.
- No alert fired for 2 hours 12 minutes because the system was healthy and
  silent. Monitoring must cover delivery outcomes, not process liveness.
- Detection came from support, 46 minutes after the failure and 81 minutes
  after a customer's experience degraded. The detection path was entirely
  outside the engineering system.
- Comparing against the last known good deployment is the fastest path to a
  silent-failure root cause. Reading the current configuration alone does not
  reveal what is missing.
- The replay was correct but produced a second, smaller incident. Replaying
  19 hours of notifications generated 312 support contacts about apparently
  duplicate or late receipts.

## Related incidents

No directly related incidents were identified at the time of writing. This is
the first recorded silent failure caused by a missing credential, and the
first recorded incident in which no monitoring signal detected the problem.

## Prevention and follow-up

- P0: Change the notification worker to fail closed. If
  `NOTIFICATION_PROVIDER_API_KEY` is absent at startup, the process must
  refuse to start.
- P0: Add a delivery-rate alert. A drop from 100 percent to 0 percent must
  page, independently of process health.
- P0: Add a synthetic end-to-end notification test every 5 minutes that
  verifies a real message was delivered, not merely dispatched.
- P1: Add a CI check that diffs the required environment variable set between
  releases and fails the build on any removal.
- P1: Write the `silent-failure-triage` runbook. Completed and committed as
  runbook `silent-failure-triage`.
- P2: Require human approval for a redeploy during an active SEV-1 or SEV-2,
  since the engineer's instinct to restart is a known failure mode.
- Owner: Messaging Platform. Tracked in MSG-880 and MSG-881.
