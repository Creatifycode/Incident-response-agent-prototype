## Summary

Production requests to `payments-api` failed with HTTP 500 starting at
14:32 UTC on 2026-02-11. The incident was triggered by deployment
`checkout-api v4.18.2` at 14:27 UTC, which introduced a database connection
pool misconfiguration. Service was restored at 14:51 UTC by rolling back the
deployment and correcting the pool configuration. Total duration was
19 minutes.

## Trigger and recent changes

At 14:27 UTC, `checkout-api v4.18.2` was deployed to production. The release
included a new connection pool implementation. Five minutes later, at 14:31
UTC, the database connection count on `orders-db-primary` began climbing
steadily, from a baseline of approximately 40 connections to 190 connections
within sixty seconds. At 14:32 UTC the first HTTP 500 responses appeared.

The triggering change was a configuration edit made as part of the release.
The new pool read `DB_POOL_MAX_CONNECTIONS` from the environment instead of
the configuration service. That environment variable was present in the
`checkout-api` container but absent from the shared `payments-api` sidecar,
which is what actually holds the production database connections. The pool
therefore fell back to an unbounded default, so every request opened a new
database connection and never released it.

## Symptoms

- HTTP 500 responses from `payments-api` on all payment authorization paths.
- Database connection count on `orders-db-primary` rose to 190 and stayed
  elevated.
- Latency on unaffected endpoints rose from roughly 120 ms to 4.8 s p99.
- `FATAL: sorry, too many clients already` errors appeared in the database log
  from 14:33 UTC.
- Upstream `checkout-api` began shedding traffic and returning its own 503s.

## Root cause

A database connection pool misconfiguration introduced by deployment
`checkout-api v4.18.2`. The pool size was sourced from an environment
variable that was not defined in the `payments-api` runtime, so the pool
opened an unbounded number of connections. Connection exhaustion on
`orders-db-primary` starved the service of database connections, producing
HTTP 500 responses.

The root cause was the configuration, not the code. The new pool code behaved
as written; the value it read was absent.

## Impact and blast radius

Infrastructure:
- 4 of 4 `payments-api` instances affected.
- `orders-db-primary` connection saturation at 190 of a 200 connection limit.
- 1 of 3 `checkout-api` instances rolled back; 2 were unaffected.

Services:
- `payments-api` degraded, effectively fully unavailable.
- `checkout-api` degraded, 503 responses to upstream callers.
- `auth-gateway` unaffected.
- `notification-worker` delayed but not failed.

Users:
- 8,200 users affected during the 19 minute window.
- Approximately 41% of payment attempts failed outright.

Requests:
- 23,400 failed requests.

Data:
- No permanent data loss.
- 17 transactions were left in `pending` state and required replay.
- Zero double charges, confirmed by reconciliation at 15:10 UTC.

## Timeline

- 14:27 - Deployment `checkout-api v4.18.2` completed to production.
- 14:31 - Database connection count on `orders-db-primary` begins climbing.
- 14:32 - First HTTP 500 responses from `payments-api`. Incident declared.
- 14:35 - On-call acknowledges page. Suspects deployment as trigger.
- 14:38 - Restart of all 4 `payments-api` instances attempted. See failed actions.
- 14:41 - Connection count briefly drops to 30, then climbs back above 190
  within ninety seconds.
- 14:43 - Engineers inspect the deployment diff. Connection pool change identified.
- 14:45 - Rollback of `checkout-api v4.18.2` initiated.
- 14:48 - Rollback complete. New connection pool no longer applied.
- 14:49 - `DB_POOL_MAX_CONNECTIONS` set to 25 in the configuration service and

- 14:51 - Service fully recovered. Error rate returned to baseline.
- 15:10 - Transaction reconciliation confirms no data loss.
- 16:30 - Incident closed.

## Attempted actions

1. Restart of all 4 `payments-api` instances, at 14:38 UTC.
2. Increased `max_connections` on `orders-db-primary` from 200 to 400, at
   14:40 UTC.
3. Rollback of `checkout-api v4.18.2` to v4.18.1, at 14:45 UTC.
4. Correction of the pool configuration, at 14:49 UTC.

## Failed actions

- Restarting the `payments-api` instances was attempted at 14:38 UTC. It did
  not resolve the incident. Connection count fell from 190 to 30 immediately
  after the restart, then climbed back above 190 within ninety seconds. A
  restart clears existing connections but does not change the pool
  misconfiguration that creates them, so the exhaustion immediately recurred.

- Increasing `max_connections` on `orders-db-primary` from 200 to 400 was
  attempted at 14:40 UTC. It did not resolve the incident. It raised the
  ceiling but the pool was still opening connections without bound, so
  saturation simply occurred later, at the new higher limit. The database
  remained the victim of the misconfiguration rather than the cause of it.

- Scaling `payments-api` from 4 to 8 instances was considered at 14:42 UTC and
  rejected without being executed. It was correctly identified beforehand as
  doubling the rate at which connections would be leaked. Had it been applied,
  it would have accelerated the outage.

## Successful actions

- Rolling back deployment `checkout-api v4.18.2` to v4.18.1 at 14:45 UTC was
  the action that reversed the failure mode. Error rate dropped from 34% to
  1.2% within three minutes of the rollback completing at 14:48 UTC.

- Setting `DB_POOL_MAX_CONNECTIONS` to 25 in the configuration service at
  14:49 UTC and restarting the `payments-api` sidecar restored full
  availability at 14:51 UTC. This corrected the root cause rather than
  masking the symptom.

## Relevant runbook

`database-connection-recovery` (runbook id `database-connection-recovery`).
The runbook was followed from step 4 onward. Steps 1 through 3 correctly
identified the trigger as a configuration change, but the incident was
resolved faster by direct rollback than by completing the full runbook.

## Lessons learned

- An environment variable that is absent at runtime does not fail loudly. The
  new pool code silently fell back to an unbounded default instead of
  refusing to start. This is the most important lesson from INC-001.
- Restarting a service is a misleading first instinct under connection
  exhaustion. It appears to work for approximately ninety seconds, which
  creates false confidence and delays the real investigation.
- Raising a database limit under an unbounded connection leak buys time and
  worsens the eventual failure. It is a delay, not a fix.
- Configuration should have a single source of truth. Two mechanisms reading
  the same pool size is what allowed the values to diverge.
- Rolling back was the highest-value action and it was reached only six
  minutes after the incident was declared. Detection was fast; correlation
  was the slow part.

## Related incidents

No related incidents were identified at the time this report was written.
This incident was the first recorded case of connection pool misconfiguration
in `payments-api`.

## Prevention and follow-up

- P0: Make the pool configuration fail closed. If `DB_POOL_MAX_CONNECTIONS` is
  unset, the service must refuse to start rather than default to unbounded.
- P0: Add a startup assertion test asserting the configured pool size is
  within the database `max_connections` budget.
- P1: Add an alert on database connection utilization above 70%.
- P1: Remove the environment variable path for pool configuration entirely and
  read only from the configuration service.
- P2: Add a runbook step for the ninety-second restart observation described
  above, so the next engineer is warned that a restart is not a fix.
