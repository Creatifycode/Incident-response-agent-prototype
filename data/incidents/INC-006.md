## Summary

Production requests to `payments-api` failed with HTTP 500 starting at
09:14 UTC on 2026-08-13. The symptom was identical to INC-001: database
connection exhaustion on `orders-db-primary` immediately following a
deployment. The root cause was different. This incident was caused by a
connection object leak in the new retry path of `checkout-api v5.2.0`, not by
a connection pool misconfiguration. Service was restored at 09:38 UTC by
rolling back `checkout-api v5.2.0`. Total duration was 24 minutes.

This incident is deliberately recorded as a case where the symptoms matched
INC-001 exactly while the root cause did not.

## Trigger and recent changes

At 09:08 UTC, `checkout-api v5.2.0` was deployed to production. The release
added automatic retry with backoff for failed database statements. Six
minutes later, at 09:14 UTC, `payments-api` began returning HTTP 500 and the
connection count on `orders-db-primary` climbed from 45 to 195.

The release did not change any pool configuration. `DB_POOL_MAX_CONNECTIONS`
was correctly set to 25 and the configuration service was correct. The pool
itself opened the correct number of connections. The problem was that each
connection was never returned to the pool.

## Symptoms

- HTTP 500 responses from `payments-api` on payment authorization paths.
- Database connection count on `orders-db-primary` rose to 195 of a 200 limit.
- Latency rose to 6.1 s p99 on affected endpoints.
- `FATAL: sorry, too many clients already` errors in the database log.
- The same signature of database connection saturation observed during INC-001.

## Root cause

A connection object leak in the retry path of `checkout-api v5.2.0`. The new
retry code acquired a database connection, attempted the statement, and on
failure returned to the retry loop without releasing the connection to the
pool. Because `orders-db-primary` emits a transient statement timeout under
load, roughly 3% of statements entered the retry path during peak traffic.
Each retry leaked one connection. At the observed request rate, the leak
exhausted the database connection limit in six minutes.

The root cause was a resource leak, not a configuration error. This is the
critical distinction from INC-001.

## Impact and blast radius

Infrastructure:
- 4 of 4 `payments-api` instances affected.
- `orders-db-primary` connection saturation at 195 of 200.
- `checkout-api` v5.2.0 running on 6 of 6 instances.

Services:
- `payments-api` fully unavailable for 24 minutes.
- `checkout-api` degraded.
- `auth-gateway` unaffected.
- `notification-worker` delayed by up to 40 minutes.

Users:
- 11,600 users affected.
- 52% of payment attempts failed.

Requests:
- 39,800 failed requests.

Data:
- No permanent data loss.
- 44 transactions left in `pending` state and required replay.
- 3 suspected duplicate authorization attempts were reversed after manual
  review, caused by client-side retry rather than by the leak itself.

## Attempted actions

1. Verification of `DB_POOL_MAX_CONNECTIONS` against INC-001, at 09:19 UTC.
2. Restart of all 4 `payments-api` instances, at 09:21 UTC.
3. Rollback of `checkout-api v5.2.0` to v5.1.4, at 09:31 UTC.

## Failed actions

- Restarting the `payments-api` instances was attempted at 09:21 UTC. It did
  not resolve the incident. This is the second recorded time a restart failed
  to resolve a `payments-api` connection exhaustion incident, the first being
  INC-001. Connection exhaustion recurred within two minutes of the restart,
  faster than the ninety seconds seen in INC-001, because the leak rate
  scales with request volume.

- Assuming the INC-001 root cause was correct and checking pool configuration
  first was attempted between 09:18 and 09:19 UTC. This did not resolve the
  incident, although it was a short and ultimately useful detour: verifying
  the configuration in 60 seconds correctly eliminated the prior hypothesis
  and redirected the investigation to the deployment. Had this not been
  checked, engineers would have continued tuning a correctly configured pool.

## Successful actions

- Verifying that `DB_POOL_MAX_CONNECTIONS` was correctly set at 09:19 UTC
  eliminated the INC-001 hypothesis in under a minute. This is the highest
  value action in the incident, because the prior incident's memory directed
  attention to the wrong cause and a fast check discarded it.

- Rolling back `checkout-api v5.2.0` at 09:31 UTC reversed the failure mode.
  Error rate fell from 41% to 0.4% within two minutes of completion at
  09:36 UTC.

## Relevant runbook

`database-connection-recovery` (runbook id `database-connection-recovery`) was
consulted at 09:18 UTC. Step 2 of that runbook, comparing pool configuration,
returned a clean result and was therefore the step that redirected the
investigation. The runbook assumes configuration is the likely cause, and
during this incident that assumption was wrong, although the runbook's
verification step is what exposed that.

## Lessons learned

- Identical symptoms do not imply an identical root cause. INC-001 and
  INC-006 both presented as database connection exhaustion immediately after
  a deployment, and the root causes were unrelated. Historical similarity is
  a starting point for investigation, not a diagnosis.
- A restart is now known to be useless in this class of incident. It has now
  failed twice, in INC-001 and in INC-006. The runbook has been updated to
  state this explicitly.
- The useful lesson from INC-001 was not the misconfiguration itself but the
  verification habit: check the configuration first, and if it is clean, stop
  tuning it. That habit cut this investigation short.
- Leaks are harder to see than misconfigurations. A misconfiguration is
  visible in config; a leak is visible only as a rate of change. Monitoring
  based on absolute connection count would not have caught this early.
- The detection to declaration gap was one minute, which is good. The
  declaration to correct hypothesis gap was 13 minutes, which is too long.

## Related incidents

This incident is a direct structural repeat of INC-001, which occurred on
2026-02-11 at 14:32 UTC. Both incidents affected `payments-api` and
`orders-db-primary`, both followed a `checkout-api` deployment, and both
involved database connection exhaustion. The root causes were different, and
the remediation for the configuration mistake recommended in INC-001 was
verified as already correctly applied at the start of this incident.

## Prevention and follow-up

- P0: Fix the connection leak in the `checkout-api v5.2.0` retry path, which
  acquired a connection and did not return it on the failure branch.
- P0: Add a connection pool saturation test to CI that fails when a code path
  can reach a retry branch without releasing its connection.
- P1: Alert on the rate of change of database connection count, not only on
  absolute utilization. INC-006 was a rate problem.
- P1: Add a `connection leak` step to the `database-connection-recovery`
  runbook, since the existing runbook assumes a configuration cause.
- P1: Add a canary deployment with connection pool metrics gating, so a leak
  is caught in the canary environment rather than in production.
