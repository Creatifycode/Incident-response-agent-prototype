## Summary

`auth-gateway` rejected valid user tokens across all regions starting at
18:03 UTC on 2026-04-22. The root cause was a configuration change to the
JWT audience validation setting, which required an issuer claim that the
identity provider did not emit. All authentication failed, and because
`auth-gateway` gates the internal service mesh, all customer-facing services
became inaccessible simultaneously. Service was restored at 18:19 UTC by
reverting the configuration. Total duration was 16 minutes.

## Trigger and recent changes

At 17:55 UTC an engineer applied a configuration change through the
configuration service, setting `jwt_require_audience_claim` to `true` on
`auth-gateway` across all 8 regions. The intent was to harden token validation
in response to a security review finding.

Eight minutes later, at 18:03 UTC, token validation began failing for all
users. The identity provider `auth0-tenant-prod` issues tokens with `iss` and
`sub` but has never emitted an `aud` claim. The new requirement was therefore
unsatisfiable for every token in existence.

No code was deployed. The change was configuration only, applied through the
standard configuration service with no code review gate.

## Symptoms

- All authenticated endpoints returned HTTP 401 from `auth-gateway`.
- Log signature: `jwt_validation_failed: required claim 'aud' not present`.
- `auth-gateway` returned 401 for valid, unexpired tokens.
- All downstream services became inaccessible because service mesh mTLS
  identity is issued through the same gateway.
- No 5xx errors. The failure was total but clean, which made it initially
  confusing to triage.

## Root cause

A configuration change to JWT audience validation. Setting
`jwt_require_audience_claim` to `true` on `auth-gateway` caused every token to
be rejected, because the identity provider does not issue an `aud` claim. The
change was applied to all regions simultaneously with no staged rollout, so
there was no partially-degraded state and no region retained working
authentication.

The root cause is a configuration change that was never validated against a
real token before being applied globally, combined with the absence of a
staged rollout for high-blast-radius configuration.

## Impact and blast radius

Infrastructure:
- 8 of 8 `auth-gateway` regional instances affected.
- No partial degradation, the change was applied globally and atomically.

Services:
- `auth-gateway` fully unavailable.
- `payments-api`, `orders-api`, `checkout-api` all inaccessible, because
  service mesh identity flows through the same gateway.
- `notification-worker` unaffected, it authenticates out of band.

Users:
- 100% of authenticated users locked out simultaneously.
- 31,000 active sessions affected.
- 6 minutes elapsed before the incident was detected by alerting, because
  alerting was configured for 5xx rates and this incident produced only 401s.

Requests:
- 112,000 failed requests.

Data:
- No data loss. The failure was entirely at the authentication gate.
- No writes occurred, because no request was authorized.
- No partial state, no reconciliation required.

## Timeline

- 17:55 - Configuration change applied: `jwt_require_audience_claim=true`,
  all 8 regions.
- 18:03 - First 401 responses observed by a synthetic monitoring check.
- 18:04 - Alert fires on customer support volume, not on the 401 rate.
- 18:09 - Incident declared SEV-1. All authentication confirmed failing.
- 18:11 - Engineers verify tokens are valid and unexpired by decoding one
  manually, establishing that the gateway is at fault, not the client.
- 18:14 - Configuration change history reviewed. The 17:55 change identified.
- 18:16 - Attempt to set `jwt_require_audience_claim` to `false` fails due to
  a schema validation error. See failed actions.
- 18:19 - Revert of the 17:55 configuration change applied via rollback.
- 18:21 - Token validation confirmed healthy in all regions.
- 18:30 - Incident closed.

## Attempted actions

1. Manual decode of a production token to establish its validity, at 18:11 UTC.
2. Direct edit of `jwt_require_audience_claim` to `false`, at 18:16 UTC.
3. Revert of the 17:55 configuration change, at 18:19 UTC.

## Failed actions

- Directly setting `jwt_require_audience_claim` to `false` at 18:16 UTC did
  not work. The attempt was rejected with a schema validation error stating
  that the field could not be modified outside the configuration service, so
  the engineers lost approximately three minutes discovering this constraint
  while production authentication was still failing. Setting the value
  directly should have been skipped in favour of a revert from the start.

- Searching for a client-side or identity provider fault was attempted between
  18:09 and 18:11 UTC and did not resolve the incident. Because the entire
  failure was at the token validation step and tokens were demonstrably valid,
  investigation of the identity provider was the wrong direction. It was
  abandoned once a token was decoded successfully at 18:11 UTC.

## Successful actions

- Manually decoding a production token at 18:11 UTC proved the tokens were
  valid and correctly signed, which immediately located the fault inside
  `auth-gateway` rather than with clients or the identity provider. This was
  the action that redirected the investigation.

- Reverting the 17:55 configuration change at 18:19 UTC restored
  authentication in all 8 regions by 18:21 UTC. Reverting a known recent
  change is faster and safer than reasoning about a new correct value, which
  is what the failed direct edit at 18:16 UTC had attempted to do.

## Relevant runbook

`auth-configuration-verification` (runbook id
`auth-configuration-verification`) was written after this incident and did not
exist at the time. Its step 1, decode a real token and list its claims before
touching configuration, is the 18:11 UTC action that resolved the direction of
this investigation.

## Lessons learned

- A hardening change can be the outage. The intent was to improve security and
  the effect was a total authentication outage.
- Alerting on 5xx rates missed a 100 percent 401 outage for six minutes. The
  alert was monitoring the wrong failure mode entirely.
- There was no staged rollout for a configuration change with total blast
  radius. One region would have failed instead of eight.
- A token validity check should precede any token validation change. The
  correct question is not "is this setting right" but "does the issuer
  actually produce tokens that satisfy it".
- Reverting is a better default than correcting under time pressure. The failed
  direct edit cost three minutes that a revert would not have.

## Related incidents

No related incidents were identified at the time of writing. This was the
first recorded authentication outage in `auth-gateway`.

## Prevention and follow-up

- P0: Add alerting on HTTP 401 rate as a first-class production signal, not
  only 5xx.
- P0: Require staged rollout, starting with a single region, for any `auth-gateway`
  configuration change.
- P0: Add a CI check that validates every token validation rule against a real
  signed test token before it can be applied.
- P1: Write the `auth-configuration-verification` runbook. Completed and
  committed as runbook `auth-configuration-verification`.
- P1: Require peer review for configuration changes on `auth-gateway`, matching
  the existing code review gate.
- P2: Add a synthetic check that performs a full login every 60 seconds and
  alerts on failure. The detection gap of 6 minutes would have been 1 minute.
